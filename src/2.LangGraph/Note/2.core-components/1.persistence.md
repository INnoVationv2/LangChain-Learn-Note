# Persistence

LangGraph 有两种互补的持久化机制：

- **Checkpointer**：保存当前线程的State，提供线程内的短期记忆，支持对话延续、人工介入、时间回溯和容错。
- **Store**：保存跨线程的持久信息，提供跨线程的长期记忆，如用户偏好、事实和共享知识。

| 对比     | Checkpointer（检查点保存器）       | Store（存储）            |
| -------- | ---------------------------------- | ------------------------ |
| 保存内容 | State快照                          | 自定义的键值数据         |
| 作用范围 | 单个线程                           | 跨线程                   |
| 记忆类型 | 线程内的短期记忆                   | 跨线程的长期记忆         |
| 适用场景 | 对话延续、人工介入、时间回溯、容错 | 用户偏好、事实、共享知识 |
| 访问方式 | 在图配置中传入 `thread_id`         | 在节点或代码中读写数据   |

## 常见问题解决方法

**1. PostgresSaver 的 `thread_id` 过长**

使用 `PostgresSaver` 或 `AsyncPostgresSaver` 时，`thread_id` 超过数据库列的长度限制会报错。

解决：将 `thread_id` 控制在 255 个字符以内。可使用 UUID；需要确定性 ID 时可使用哈希。

**2. MemorySaver 重启后数据丢失**

`MemorySaver` 和 `InMemorySaver` 将检查点保存在内存中，进程重启后全部丢失。

解决：改用持久化检查点保存器：

- `PostgresSaver`：基于 PostgreSQL，支持异步，适合生产环境。
- `SqliteSaver`：基于本地文件，适合开发环境。

**3. Checkpoint持续增长**

长对话会不断累积检查点，增加延迟和存储成本。

解决：定期清理旧检查点，或设置保留策略。

**4. 父图无法立即看到子图的状态更新**

每个子图管理自己的检查点命名空间，因此父图可能无法立即看到子图的状态变化。

解决：通过 `Store` 共享跨图数据，或配置子图将状态写入父图的检查点。

# 1.Checkpoint

## 1.Checkpoint提供的功能

- **人机协同**：通过中断`(interrupt)`实现人工检查、中断和批准继续执行，并在修改状态后恢复执行。
- **记忆**：保存同一thread_id的历史交互数据
- **时间回溯**：重放历史执行，检查或调试特定步骤；也可以从任意检查点创建分支，探索不同执行路径。
- **容错恢复**：某个超级步中的节点失败时，可从最近成功的步骤恢复执行。
- **待写入数据（Pending writes）**：同一超级步中，部分节点失败时，LangGraph 会保留其他已成功节点的检查点写入数据，恢复时无需重复执行这些成功节点。

## 2.基础概念

1. Checkpoint

   检查点是每个SuperStep保存的图State快照，由`StateSnapshot`对象表示

2. SuperStep

   SuperStep是图的一轮执行：该轮调度的所有节点都会执行，也可能并行执行。每步结束后都会生成检查点。

   时间回溯只能从完整检查点恢复，即从SuperStep边界恢复。

   除了完整检查点，LangGraph还会保存SuperStep内各节点的执行结果：

   - 每个节点完成后，其输出会作为任务记录写入 `checkpoint_writes` 表，关联到正在生成的检查点。
   - 如果同一超级步中的其他节点失败，恢复时可以复用已成功节点的结果，无需重新执行。
   - 整个超级步完成后，再提交完整的状态快照。

   节点级的状态只能用于容错恢复，不是完整的 `StateSnapshot` 检查点，不能作为时间回溯的恢复位置。

   > 例如，A、B 在同一个超级步中并行执行：
   >
   > ```
   > A 成功 → 保存 A 的结果
   > B 失败 → 这一轮尚未形成完整检查点
   > ```
   >
   > 此时有两种情况：
   >
   > - **失败后恢复**：直接复用 A 的结果，只重新执行 B。
   > - **时间回溯**：只能选择某个完整检查点，不能选择“A 已完成、B 尚未完成”这个中间位置

3. Checkpoint namespace

   每个检查点都有 `checkpoint_ns` 字段，用于标识它属于哪个图或子图：

   | 值                                  | 含义                          |
   | ----------------------------------- | ----------------------------- |
   | `""`（空字符串）                    | 属于根图                      |
   | `"node_name:uuid"`                  | 属于以该节点名调用的子图      |
   | `"outer_node:uuid|inner_node:uuid"` | 属于嵌套子图，各层用 `|` 分隔 |

   可以在节点内通过 `config` 获取命名空间：

   ```ts
   function myNode(state: typeof State.Type, config: RunnableConfig) {
     const checkpointNs = config.configurable?.checkpoint_ns;
     // 根图为 ""，子图为 "node_name:uuid"
   }
   ```

## 3.获取和更新State

### 3.1 获取State

```ts   
//获取Graph的最新State snapshot
const config = {configurable: {thread_id: "1"}};
await graph.getState(config);

// 获取指定Checkpoint的State snapshot
const config = {configurable: {thread_id: "1", checkpoint_id: "xxxx"}};
await graph.getState(config);
```

### 3.2 获取State history

```ts
const config = { configurable: { thread_id: "1" } };
for await (const state of graph.getStateHistory(config)) {
  console.log(state);
}
```

获取给定Thread的完整图执行历史记录。返回的Checkpointe将按时间顺序排列.

### 3.3 找到指定Checkpoint

通过筛选State历史记录, 查找符合条件的检查点：

```ts
const history: StateSnapshot[] = [];
for await (const state of graph.getStateHistory(config)) {
  history.push(state);
}

// Find the checkpoint before a specific node executed
const beforeNodeB = history.find((s) => s.next.includes("nodeB"));

// Find a checkpoint by step number
const step2 = history.find((s) => s.metadata.step === 2);

// Find checkpoints created by updateState
const forks = history.filter((s) => s.metadata.source === "update");

// Find the checkpoint where an interrupt occurred
const interrupted = history.find(
  (s) => s.tasks.length > 0 && s.tasks.some((t) => t.interrupts.length > 0)
);
```

### 3.4 Replay和Fork

可通过检查点进行时间旅行：

- **重放(Replay)**：从之前的检查点重新执行。
- **分支(Fork)**：从先前的检查点创建分支，并修改其状态以探索替代路径。

#### Replay

使用某个`state snapshot`, 重新执行该检查点之后的步骤。

```ts
const config = {configurable: {thread_id: "1"}};
const stateSnapshot = await graph.getState(config);

const replayResult = await graph.invoke(null, stateSnapshot.config);
```

#### Fork

```ts
const config = {configurable: {thread_id: "1"}};
const stateSnapshot = await graph.getState(config);

// update_state不是回滚线程, 而是创建一个新的检查点. 原始执行历史记录不变
const forkConfig = await graph.updateState(
  stateSnapshot.config, {cnt: 1});

const forkResult = await graph.invoke(null, forkConfig);
console.log(forkResult.joke);
```

**asNode**

默认情况下，会从`stateSnapshot`对应的节点继续执行, 可通过 asNode 从指定节点开始执行。

```ts
const stateSnapshot = await graph.updateState(
  beforeJoke.config,
  { cnt: 1 },
  { asNode: "generateTopic" },
);
```

#### Subgraph

对子图进行replay或fork。取决于子图是否拥有自己的检查点。

1. 默认检查点设置

   默认情况下，父图将整个子图视为一个单独的Super Step, 整个子图在执行过程中只有一个父级检查点。因此无法对子图进行replay或fork, 只能从父级开始执行。

2. 开启子图检查点

   在子图设置`checkpointer=True`，使其拥有自己的检查点历史记录。这会在子图的每个步骤创建检查点.

   ```ts
   const subgraph = new StateGraph(StateAnnotation)
     .addNode("stepA", stepA)
     .addNode("stepB", stepB)
     .addEdge(START, "stepA")
     .addEdge("stepA", "stepB")
     .compile({ checkpointer: true }); // 开启子图检查点
   
   const graph = new StateGraph(StateAnnotation)
     .addNode("subgraphNode", subgraph)
     .addEdge(START, "subgraphNode")
     .compile({ checkpointer });
   
   await graph.invoke({ value: [] }, config);
   await graph.invoke(new Command({ resume: "Alice" }), config);
   
   const parentState = await graph.getState(config, { subgraphs: true });
   const subConfig = parentState.tasks[0].state.config;
   
   const forkConfig = await graph.updateState(subConfig, { value: ["forked"] });
   const result = await graph.invoke(null, forkConfig);
   ```

## 4. 持久化模式

```ts
await graph.stream(
  { input: "test" },
  { durability: "sync" }
)
```

持久化模式按可靠性从低到高排列：

| 模式      | 保存时机                                         | 特点                                                         |
| --------- | ------------------------------------------------ | ------------------------------------------------------------ |
| `"exit"`  | 图执行退出时保存，包括成功、报错或人工介入中断。 | 长时间运行的图性能最佳，但不保存中间状态，无法从执行途中的进程崩溃等系统故障中恢复。 |
| `"async"` | 执行下一步的同时，异步保存。                     | 兼顾性能和可靠性，但进程崩溃时，存在少量检查点未写入的风险。 |
| `"sync"`  | 同步保存完成后，才执行下一步。                   | 确保每个检查点写入后再继续，可靠性高，但有一定性能开销。     |

## 5.其他

### Checkpointer 库

Checkpointer 遵循 `BaseCheckpointSaver` 接口。LangGraph 提供以下独立库：

| 库                                         | 实现与用途                                                   | 安装           |
| ------------------------------------------ | ------------------------------------------------------------ | -------------- |
| `@langchain/langgraph-checkpoint`          | 提供基础接口 `BaseCheckpointSaver`、序列化与反序列化接口 `SerializerProtocol`，以及用于实验的内存实现 `MemorySaver`。 | LangGraph 自带 |
| `@langchain/langgraph-checkpoint-sqlite`   | 基于 SQLite 的 `SqliteSaver`，适合实验和本地工作流。         | 单独安装       |
| `@langchain/langgraph-checkpoint-postgres` | 基于 PostgreSQL 的 `PostgresSaver`，用于 LangSmith，适合生产环境。 | 单独安装       |
| `@langchain/langgraph-checkpoint-mongodb`  | 提供 `MongoDBSaver` 和长期记忆存储 `MongoDBStore`。后者支持跨线程持久化，可选集成向量搜索，适合生产环境。 | 单独安装       |
| `@langchain/langgraph-checkpoint-redis`    | 基于 Redis 的 `RedisSaver`，适合生产环境。                   | 单独安装       |

### Checkpointer 接口

每个 Checkpointer 都实现了以下方法：

| 方法         | 作用                                                         |
| ------------ | ------------------------------------------------------------ |
| `.put`       | 保存检查点及其配置、元数据。                                 |
| `.putWrites` | 保存关联到检查点的中间写入，即待写入数据（pending writes）。 |
| `.getTuple`  | 根据配置中的 `thread_id` 和 `checkpoint_id` 获取检查点元组，用于构建 `graph.getState()` 返回的 `StateSnapshot`。 |
| `.list`      | 按配置和筛选条件列出检查点，用于构建 `graph.getStateHistory()` 返回的状态历史。 |

# 2.Store

> 本章节使用`InMemoryStore`作为案例, `InMemoryStore`适用于开发和测试。生产环境需切换成持久化存储，例如`PostgresStore`、`MongoDBStore`或`RedisStore`。

## 2.1 基本用法

Store是按照namespace进行存储的。

Namespace的类型是`[]string`。表示分层路径，每个元素代表一层，而不是多个独立的命名空间。类似文件夹路径.

```ts
const store = new InMemoryStore();
// 增
await store.put(['namespace'], "1", {"name": "luke", age: 18})
// 查
let result = await store.get(['namespace'], "1")
console.log(result);
// 改
await store.put(['namespace'], "1", {"name": "Zebra", age: 88})
result = await store.get(['namespace'], "1")
console.log(result);
// 删
await store.delete(['namespace'], "1")
```

## 2.2 namespace相关操作

```ts
// search: 获取namespace的所有item
await store.put(['namespace'], "1", {"name": "luke", age: 18})
await store.put(['namespace'], "2", {"name": "Zebra", age: 88})
const items = await store.search(['namespace']);
items.forEach((item) => console.log(item));

// 可限制每次获取的数量
const items = await store.search(['namespace'], {limit: 100});
// 也可使用分页功能
const items = await store.search(['namespace'], {limit: pageSize, offset});

// 查找namespace
const namespaces = await store.listNamespaces({ prefix: ["alice"], maxDepth: 2 });
```

注:

1.  Store的搜索都是前缀匹配, 因此`["alice"]` 也会匹配 `["alice", "memories"]`、`["alice", "preferences"]` 等子命名空间。需要精确匹配时, 需要传入完整命名空间.
2. 如果设置了limit, 超出会直接截断, 不会提示还有更多数据。
3. 默认存储顺序因实现而异：
   - `PostgresStore`、`AsyncPostgresStore`：按 `updated_at` 降序，最近更新的在前。
   - `InMemoryStore`：按插入顺序，最近插入的在后。
   - 如需统一顺序，可自行排序。

## 2.2 语义搜索

Store还支持语义搜索，允许根据含义查找。要启用此功能，需使用嵌入模型配置存储：

```ts
const store = new InMemoryStore({
  index: {
    embeddings: new OpenAIEmbeddings({ model: "text-embedding-3-small" }),
    dims: 1536,
    fields: ["food_preference", "$"], // Fields to embed
  },
});

// 然后就可以使用自然语言来查询了
const memories = await store.search(namespaceForMemory, {
  query: "What does the user like to eat?",
  limit: 3, // Return top 3 matches
});
```

通过配置 `fields` 参数，或在保存时指定 `index`，可控制哪些字段生成嵌入向量：

- `fields` 是默认设置
- `index` 是单次保存的设置

```ts
// 仅为food_preference字段生成嵌入向量
await store.put(
  namespaceForMemory,
  crypto.randomUUID(),
  {
    food_preference: "我喜欢意大利菜",
    context: "讨论晚餐计划"
  },
  { index: ["food_preference"] }
);

// 不生成嵌入向量：仍可读取，但不参与语义搜索
await store.put(
  namespaceForMemory,
  crypto.randomUUID(),
  { system_info: "最后更新：2024-01-01" },
  { index: false }
);
```
