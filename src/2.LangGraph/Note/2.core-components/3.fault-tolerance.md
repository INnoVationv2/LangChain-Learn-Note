# 容错

当节点发生故障时(例如外部 API 响应缓慢、突发网络错误或未处理的异常)，LangGraph 提供三种可组合使用的应对机制：

- **重试(Retries)**：根据异常类型和退避设置，自动重新执行失败的操作。
- **超时(Timeout)**：限制单次尝试的最长运行时间。
- **错误处理(Error handling)**：重试次数耗尽后，执行恢复函数。

使用`setNodeDefaults`配置这些机制.

## 1. 重试

获取重试信息

```ts
const nodeA = (state: typeof stateSchema.State, runtime: Runtime<typeof stateSchema>) => {
    if (runtime.executionInfo?.nodeAttempt ?? 1 > 1)
        return {};
    return {};
}
```

可通过executionInfo获取重试次数, Executioninfo 有以下字段。

| 属性                   | 类型                 | 说明                                                      |
| ---------------------- | -------------------- | --------------------------------------------------------- |
| `nodeAttempt`          | `number`             | node执行次数，首次执行为 1，第一次重试为 2，以此类推。    |
| `nodeFirstAttemptTime` | `number | undefined` | 首次执行的Unix时间戳（毫秒），重试期间保持不变。          |
| `threadId`             | `string | undefined` | 当前执行的线程 ID。未配置 checkpointer 时为 `undefined`。 |
| `runId`                | `string | undefined` | 当前执行的运行 ID。未在 config 中提供时为 `undefined`。   |
| `checkpointId`         | `string`             | 当前执行的检查点 ID。                                     |
| `checkpointNs`         | `string`             | 当前执行的检查点命名空间。                                |
| `taskId`               | `string`             | 当前执行的任务 ID。                                       |

即使未配置重试策略，也可以使用 `executionInfo`，此时 `nodeAttempt` 默认为 `1`。

## 2.超时

设置`timeout`超时

```ts
.addNode('nodeA', nodeA, {timeout: 10000})
```

### `runTimeout`和`idleTimeout`

- `runTimeout:`Node 最长执行时间, 默认的timeout就等于`runtimeout`
- `idleTimeout:`Node 连续没有进展信号的最长时间，有进展时重新计时。

```ts
.addNode('nodeA', nodeA, {timeout: 10000})
// 等价于
.addNode('nodeA', nodeA, {timeout: 10000})
```

默认 `refreshOn: "auto"` 下，以下行为算报告进展：

- 通过图的写入路径更新State
- 通过 `runtime.writer` 输出自定义流数据
- 调度子任务
- 触发LangChain回调事件，如 LLM token 输出、工具调用、链开始或结束等
- 手动心跳

### 手动心跳

设置`refreshOn: "heartbeat"`: 仅显式调用`runtime.heartbeat()`会重置idle计时器

```ts
.addNode('nodeA', nodeA, {
  timeout: {idleTimeout: 3000, refreshOn: 'heartbeat'}})

// 显示调用heartbeat
runtime.heartbeat?.();
```

### Timeout Error

超时触发时，LangGraph 会抛出 `NodeTimeoutError`，包含具体超时信息：

| 属性          | 类型                 | 说明                                                 |
| ------------- | -------------------- | ---------------------------------------------------- |
| `node`        | `string`             | 执行超时的节点名称。                                 |
| `elapsed`     | `number`             | 超时触发前已耗时（毫秒）。                           |
| `kind`        | `"idle" | "run"`     | 触发的超时类型：空闲超时或运行超时。                 |
| `timeout`     | `number`             | 本次触发的超时阈值（毫秒）。                         |
| `idleTimeout` | `number | undefined` | 配置的空闲超时时间（毫秒），未配置时为 `undefined`。 |
| `runTimeout`  | `number | undefined` | 配置的运行超时时间（毫秒），未配置时为 `undefined`。 |

可以使用`isNodeTimeoutError(error)`来缩小捕获的错误范围。

`NodeTimeoutError`默认是可重试的。可以与重试策略结合使用, 每次重试时超时时钟都会重置，底层依赖Checkpoint, 重试会使用之前存储的状态重复执行, 因此超时尝试的写入操作会在重试之前被清除：

```ts
const graph = new StateGraph(State)
  .addNode("callModel", callModel, {
    timeout: { idleTimeout: 30_000 },
    retryPolicy: { maxAttempts: 3 },
  })
  .compile();
```

### 使用Send设置超时时长

```ts
const fanOut = (state: typeof State.State) =>
  state.items.map(
    (item) => new Send("processItem", { item }, 
                       { timeout: { idleTimeout: 15_000 } })
  );
```

## 3.错误处理

自定义错误处理方法, 当节点发生故障且重试次数用尽后会执行。

该方法可以接收当前状态，并可以使用`Command`更新状态或将其路由到其他节点。

```ts
const paymentErrorHandler = 
(state: typeof State.State, error: NodeError) => 
new Command({
  update: { status: error.error.message },
  // 路由到finalize节点
  goto: "finalize",
});

.addNode("chargePayment", chargePayment, {
  retryPolicy: {
    maxAttempts: 3,
    retryOn: (err) => err instanceof ConnectionError,
  },
  errorHandler: paymentErrorHandler,
})
```

**NodeError**类型

| 属性    | 类型     | 说明                 |
| ------- | -------- | -------------------- |
| `node`  | `string` | 执行失败的节点名称。 |
| `error` | `Error`  | 失败节点抛出的异常。 |

### `interrupt()`调用

> 在节点内部调用`interrupt()`**不会**被路由到错误处理程序。中断使用GraphBubbleUp机制来实现`interrupt()`，从而绕过重试策略和错误处理程序。

###  Subgraph failures

如果节点调用子图，并且该子图引发了一个未处理的异常，该异常会传递给父节点。如果父节点有错误处理程序，子图的异常及错误信息会被传递给它。

## 4.默认值

使用`setNodeDefaults`为所有Node设置默认的容错配置

```ts
const graph = new StateGraph(State)
  .setNodeDefaults({
    retryPolicy: { maxAttempts: 3 },
    errorHandler: defaultErrorHandler,
    timeout: { runTimeout: 30_000 },
    cachePolicy: { ttl: 60 },
  })
  .addNode("stepA", stepA)
  ......
```

### 覆盖默认值

设置了默认值后, 仍可为Node传入设置, 这些设置会覆盖默认值, 其他Node仍使用默认值.

```ts
const graph = new StateGraph(State)
  .setNodeDefaults({ errorHandler: defaultErrorHandler })
  .addNode("stepA", stepA)
  .addNode("stepB", stepB, { errorHandler: customErrorHandler }) 
  .addEdge(START, "stepA")
  .compile();
```

### 错误处理程序使用范围

默认配置并不适用于所有节点。如下图所示, 错误处理节点不适用部分默认配置：

| `setNodeDefaults` 参数 | 普通节点 | 错误处理节点 | 原因                                 |
| ---------------------- | -------- | ------------ | ------------------------------------ |
| `retryPolicy`          | ✅        | ✅            | 错误处理节点遇到临时故障时也应重试。 |
| `timeout`              | ✅        | ✅            | 错误处理节点卡住时，也应取消执行。   |
| `errorHandler`         | ✅        | ❌            | 错误处理节点不能捕获自身的异常。     |
| `cachePolicy`          | ✅        | ❌            | 缓存错误处理结果不安全。             |

> `cachePolicy`设置的是 **LangGraph 节点执行结果的缓存策略**。
>
> 例如查询订单：
>
> ```
> 输入 orderId=123 → 执行节点，缓存结果
> 再次输入 orderId=123 → 命中缓存，直接返回结果，跳过节点执行
> ```

### 默认值范围

父图设置的默认值**不会**被子图继承。每个图都维护自己的默认值。

## 5. 为Function API设置容错参数

```ts
const callApi = task(
  {
    name: "callApi",
    timeout: { idleTimeout: 30_000 },
    retry: { maxAttempts: 3 },
  },
  async (url: string) => {
    const response = await fetch(url);
    return response.text();
  }
);

const myWorkflow = entrypoint(
  { name: "myWorkflow", timeout: 60_000 },
  async (inputs: { url: string }) => {
    return await callApi(inputs.url);
  }
);
```

## 6.优雅的关机

使用`RunControl`实现`Drain`协作式关机功能, 能够在当前超级步完成后停止正在进行的图，并保存一个可恢复的检查点。

```ts
const runControl = new RunControl();

const nodeA: typeof stateSchema.Node = async () => {
    console.log("NodeA")
    //100ms后请求停止
    setTimeout(() => {
        console.log("请求停止");
        runControl.requestDrain("demo");
    }, 100);
}
```

`Drain`是协作式停止机制，在超级步之间生效，不会中断正在执行的Node。

| 场景                                    | 行为                                                         |
| --------------------------------------- | ------------------------------------------------------------ |
| 节点正在执行                            | 节点执行完成后，在下一个超级步开始前生效                     |
| 节点正在按重试策略重试                  | 等待重试成功或次数耗尽后生效                                 |
| 图自然结束与 Drain 恰好发生在同一轮调度 | 正常返回，可检查 `control.drainRequested` 区分是否请求过 Drain |
| 还有后续超级步                          | 抛出 `GraphDrained(reason)`，保存检查点，支持恢复            |
| 子图请求 Drain                          | `GraphDrained` 向父图传播，父图在自身下一个超级步边界停止    |

### 恢复执行

停止后可使用相同的`thread_id`,通过`invoke(null, config)`恢复执行。

```ts
console.log("恢复运行");
await graph.invoke(null, config);
```

### 主动停机

节点可以通过 `runtime` 读取 Drain 状态，主动退出.

```ts
const myNode = async (state: typeof State.State, runtime: Runtime<typeof State>) => {
	// 发现已经有Drain请求, 主动退出
	if (runtime.control?.drainRequested)
		return { status: "skipped", reason: runtime.control.drainReason };

  return { status: await doWork() };
};
```

### 监听SIGTERM

处理进程关闭时，推荐监听 `SIGTERM` 并请求 Drain：

```ts
const control = new RunControl();
process.on("SIGTERM", () => control.requestDrain("sigterm"));
```

## 7.限制

- **子图不继承 `setNodeDefaults`**：每个图独立管理自己的默认配置。
- **错误处理器仅支持 `StateGraph`**：通过 `StateGraph.addNode` 的 `errorHandler` 参数设置，基础 `Graph` 类、`task` 和 `entrypoint` 均不支持。
- **每个节点最多一个处理器**：每个节点最多配置一个 `errorHandler`。
- **处理器自身的异常会向上传播**：如果错误处理器抛出异常，该异常会像节点未配置处理器时一样向上传播。
