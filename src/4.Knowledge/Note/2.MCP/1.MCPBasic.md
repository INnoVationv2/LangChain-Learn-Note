# MCP基础

MCP(Model Context Protocol): 是一个开源标准,用于将 AI 应用连接到外部系统.

借助 MCP,ChatGPT 等 AI 应用可以连接数据源(如本地文件、数据库)、Tool(如搜索引擎、计算器)和工作流(如专用Prompt),从而能够获取相关信息并执行任务.

**MCP能实现哪些功能？**

* 访问你的Google日历和Notion,成为更个性化的 AI 助手.
* 可以根据Figma设计稿生成完整的 Web 应用.
* 聊天机器人可以连接组织内的多个数据库,让用户通过聊天分析数据.
* 可以在Blender中创建 3D 设计,并用 3D 打印机打印出来.

## 基础概念

- **MCP 主机**: 协调和管理若干个MCP客户端的AI应用(如Codex)
- **MCP 客户端**: 与MCP服务器保持连接, 并从服务器获取上下文供 MCP 主机使用, MCP主机为每个MCP服务器创建一个客户端,该客户端负责与对应的服务器保持连接.
- **MCP 服务器**:向 MCP 客户端提供上下文

比如 Codex 连接一个 MCP Server, Codex就会创建一个客户端与 MCP Server-A 保持连接, 当连接 MCP Server-B 时, 会创建另一个客户端

两种传输机制:

- **Stdio 传输**: 使用标准输入/输出流,在本地进程之间通信,无网络开销,性能最佳, 通常运行在本地, 只服务单个客户端, 通常被称为**本地MCP服务器**

- **Streamable HTTP 传输**: 使用 HTTP POST进行客户端到服务器的消息通信,并可选用服务器发送事件(SSE)实现流式传输.支持远程服务器通信, 标准 HTTP身份验证方式,包括 Bearer令牌、API 密钥和自定义请求头.建议使用 OAuth 获取身份验证令牌.

  通常会服务多个MCP客户端, 通常被称为**远程MCP 服务器**.

# LangChain使用MCP

## 1.MCP TOOL

### 结构化输出

Tool 返回结构化内容时, adapter不会将其放入模型可见的文本中, 而是作为`artifact`附加到`ToolMessage`上.

运行 Agent 后, 从返回的`ToolMessage`中读取`artifact`.它是一个 MCP 结果数组, 其中`type: "mcp_structured_content"`条目的`data`字段保存了Tool返回的`structuredContent`.

```ts
// adapter 将MCP返回的结果保存在`artifact`数组中.
// 找到`mcp_structured_content`条目, 读取`data`
for (const message of result.messages) {
  if (ToolMessage.isInstance(message) && Array.isArray(message.artifact)) {
    const structured = message.artifact.find(
      (entry) => entry.type === "mcp_structured_content");
    if (structured)
      console.log(`Structured content: ${JSON.stringify(structured.data)}`);
  }
}
```

### 错误处理

通过Agent调用Tool时, 如果出错,`adapter`会生成`status: "error"`的`ToolMessage`, 并附带错误信息.模型可读取错误信息并重试.

若发生传输故障,`adapter`会抛出异常；但Agent默认会将异常转换为错误`ToolMessage`.因此, 仅凭`status`无法区分错误原因.

```ts
 for (const message of result.messages)
   if (ToolMessage.isInstance(message) && message.status === "error")
     console.log(`Tool error: ${message.text}`);
```

如果直接调用Tool, 当出错时, 会抛出`ToolException`, 错误详情保存在`error.result`中

```ts
try {
  const result = await tool.invoke({ city: "上海" });
} catch (error) {
  console.log(error.result);
}
```

### Tool Metadata

MCPTool的元数据存储在`tool.metadata.annotations`中：

```ts
tool.metadata;
// {
//   annotations: {
//     destructiveHint: true,
//     readOnlyHint: false,
//   },
// }
```

`annotations`保存 MCP 服务器提供的Tool标注, 例如`readOnlyHint`和`destructiveHint`.

> Tool标注: Tool的行为说明, 帮助客户端判断Tool是否会修改或删除数据.只是提示, 不是permissions控制, 也不保证准确.
>
> ```ts
> server.registerTool("delete_file", {
>   annotations: {
>     readOnlyHint: false,
>     destructiveHint: true,
>   },
> });
> ```
>
> -`readOnlyHint: true`：Tool只读取数据, 不会修改.
> -`destructiveHint: true`：Tool可能删除、覆盖或破坏数据.
> -`destructiveHint: false`：Tool会修改环境, 但通常只是新增数据.
>
>`destructiveHint`只有在`readOnlyHint: false`时才有意义.

读取元数据时, 应提供默认值, 避免字段缺失导致错误.

### 人工审核

读取Tool标注后, 可以根据Tool类型决定是否需要审批, 不必写死Tool名称.标注描述Tool行为,  人工审核中间件负责审批.

发现Tool时, 先从`metadata`中读取`destructiveHint`.然后在审批配置中添加`when`判断函数, 之后判断每次Tool调用是否需要审批.

### Tool执行时请求用户输入

如果某个Tool需要用户输入,`MCPAdapter`会将`Elicitation(输入请求)`转换为`interrupt`, 暂停Agent, 流程如下

1. 向用户展示输入请求.
2. 获取用户回答.
3. 使用相同的`thread_id`恢复运行, 因此Agent必须配置`checkpointer`

> 恢复时, Tool会从头重新执行.请求输入前已完成的操作会重复, 因此应支持安全重试.

使用`createMCPElicitationResume`生成恢复数据, 系统会把答案关联到对应`interrupt`.不要直接传递`{responses}`, 无法确定回答属于哪个中断.

`MCPElicitationInterrupt`包含：

```
-type: "mcp_elicitation"`
-server：服务器名称
-tool：原始Tool名, 不包含前缀
-arguments：Tool调用参数
-requests：服务器的输入请求
```

如果Agent还可能产生HITL中断, 应先检查`type`, 然后处理.

多个Tool同时暂停时, 必须回答所有中断, 如果只回答第一个中断, 其他中断会保持暂停.

adapter会将回答转发给服务器, 最终结果由服务器决定, 回答有三种：

-`accept`：提供与请求Schema匹配的`content`；或者只是确认已完成网页操作, 可以不传`content`.
-`decline`：拒绝提供信息.
-`cancel`：用户取消操作.

## 2.连接

当不再使用MCP服务时, 应关闭Adapter, 根据使用场景决定 Adapter的存活时间：

| 使用场景         | 使用方式                                        | 参考内容                                                     |
| ---------------- | ----------------------------------------------- | ------------------------------------------------------------ |
| 单次Agent调用    | 创建Adapter, 运行Agent, 然后在`finally`中关闭 | [连接生命周期](#连接生命周期)                                |
| 长期运行的Worker | 复用同一个 Adapter, 在服务关闭时释放连接        | [扩展部署](https://docs.langchain.com/oss/javascript/langchain/mcp/connections#scale-a-deployment) |

### 连接生命周期

创建Adapter时只验证配置, 不会立即连接服务器.

执行以下方法时才会建立连接：`listTools()`,`listToolsets()`,`getClient()`,`Resource相关方法`

` await adapter.close();`会中止工作, 关闭连接并清除缓存.可以再次调用`listTools()`重新连接. 

### 多台服务器

  一个adapter可以同时连接多个服务器.

```ts
const adapter = new MCPAdapter({
  defaultToolTimeout: 30_000,
  servers: {
    weatherMCP: {
      transport: 'stdio',
      command: 'node',
      args: ['/Users/liuyu/work/langchain_learn/src/4.Knowledge/Code/2.MCP/1.MCPServer.ts']
    },
    LangChainDocMCP: {
      url: "https://docs.langchain.com/mcp"
    }
  }
});

// 按MCP服务器名对Tool进行分组
const toolSet = await adapter.listToolsets();
// 返回Tool List
const toolSet = await adapter.listTools();
```

默认情况下, adapter会在Tool名前加上服务器名, 例如`weatherMCP_getWeather`和`LangChainDocMCP_search`.

设置`prefixToolNameWithServerName: false`可使用原始名称.

设置超时时间`defaultToolTimeout`(单位：毫秒), 该时间会应用于所有Tool.且该配置的优先级更高, 会覆盖服务器的配置`.

### 扩展部署

默认情况下, Tool发现遇到连接失败会直接抛出异常.可通过设置`onConnectionError: "ignore"`或提供回调函数, 使Adapter忽略故障 Server, 继续连接其他服务器.

Server 重启会使旧连接失效, 需要重新调用`listTools()`, 获取最新的Tool List.

**非认证错误**会让连接失败的Server被标记为跳过.即使使用`cacheMode: "refresh"`, 也不会重试.需先调用`close()`清除状态, 认证错误会在下次发现Tool时重试.

不同传输方式支持不同的恢复机制, Stdio 支持`restart`；HTTP 和 SSE 在`mode: "legacy"`下支持`reconnect`.重新连接后调用`listTools()`, 即可获得最新的`Tool List`.

**现代 MCP Server**通常无会话, 可以使用普通负载均衡；旧版有会话的 Server 需要粘性路由, 将同一会话的请求始终发送到同一实例.

假设Agent连接了A、B两个MCP Server：

- **现代Server**：请求发给A或B都可以.

- **旧版有会话的Server**：同一个会话的请求要一直发给 A, 因为会话信息保存在 A 中.

如果 A 要求用户补充信息, 但用户回答被发送到 B, B 会验证回答携带的`requestState`.因此, 现代Server的多个实例必须共享`requestState`签名密钥, 否则验证会失败.

### 缓存

MCP SDK 会在内存中缓存Tool List.服务器返回的超时时长`ttlMs`未超时时, 重复获取Tool不会发送网络请求；若已超时, 则会重新获取.

可通过`cacheMode`控制Tool缓存：

-`"use"`：默认值.有可用缓存时优先使用.
-`"refresh"`：重新获取Tool并缓存.
-`"bypass"`：重新获取, 但不更新缓存.

```ts
// 空数组 `[]` 表示所有服务器.
const tools = await adapter.listTools([], {
  cacheMode: "refresh",
});
```

如果服务器返回的Tool描述没有变化, Adapter会复用已创建的LangChain Tool对象.

重新发现Tool只会返回最新的Tool, 但不会更新Agent的Tool List.需要下次创建 Agent时传入最新的`tools`.

### 连接协议

Adapter会为每个Server单独协商MCP协议, 同一个Adapter可以同时连接现代和旧版Server.

旧版协议使用`initialize`握手, 现代协议使用`server/discover`发现能力.每个 Server 可独立设置`mode`：

-`"auto"`：默认值.优先使用现代协议, 不支持时回退到旧版.
-`"modern"`：必须使用`2026-07-28`协议, 失败时不回退.
-`"legacy"`：使用旧版协议.

```ts
const adapter = new MCPAdapter({
  servers: {
    current: { url: modernUrl, mode: "modern" },
    legacy: { url: legacyUrl, mode: "legacy" },
  },
});
```

`"auto"`模式下, 如果 Streamable HTTP 请求返回`404`或`405`, Adapter 会依次尝试：

1. 使用原 URL 连接 SSE.
2. 将末尾的`/mcp`替换为`/sse`后重试.

`"legacy"`模式下, 任何`4xx`响应都会触发回退, 除非设置：

```
automaticSSEFallback: false
```

`setLoggingLevel()`仅支持旧版协议.如果 Server 使用现代协议, 调用它会抛出异常；现代 Server 应单独配置`logLevel`.

## 3.验证

多数远程 MCP Server 需要认证.每个HTTP或SSE Server都可以单独配置`authProvider`和`headers`：`authProvider`会原样传给`MCP SDK Transport`,`headers`会每次请求发送.`Stdio Server`不支持这两项配置.

认证方式：

- 应用管理的凭证：使用请求头或 Token Provider.
- OAuth 2.1：使用 OAuth Client Provider.
- 每次请求使用调用者身份：使用按用户认证.

### Bearer Token(持有者令牌)

如果使用固定 API Key，可以直接发送静态的`Authorization`请求头。

如果令牌由应用签发或定期轮换，可传入`authProvider({token, onUnauthorized?})`

下面这个案例, 使用一个自己实现的tokenStore。

- `current()`获取token
- `refresh()`保存新token并报告是否成功。

```ts
import { MCPAdapter, UnauthorizedError } from "@langchain/mcp-adapters";

const adapter = new MCPAdapter({
  servers: {
    search: {
      url: "https://search.example.com/mcp",
      headers: {Authorization: `Bearer ${process.env.SEARCH_API_KEY}`},
    },
    crm: {
      url: "https://crm.example.com/mcp",
      authProvider: {
        token: async () => tokenStore.current(),
        onUnauthorized: async () => {
          if (!(await tokenStore.refresh()))
            throw new UnauthorizedError("No newer token for the CRM server");
        },
      },
    },
  },
});
```

- `token()`：每次请求前执行, 获取当前 Token.
- `onUnauthorized()`：可选. 收到`401`后执行, 然后重试一次.没有新 Token 时应抛出`UnauthorizedError`.

### OAuth 身份验证

OAuth 让用户授权应用访问 MCP 服务器。将 `OAuthClientProvider` 作为 `authProvider` 传入：

- SDK 负责服务发现、客户端注册、授权码交换和令牌刷新。

- 应用负责存储、浏览器跳转和回调处理。

按照 SDK 的 OAuth 客户端指南实现 provider：

- 将 `redirectUrl` 设为回调地址。
- 保存客户端信息、令牌、PKCE 校验码和服务发现状态。
- 实现 `invalidateCredentials()`，在刷新凭证被拒绝时重新登录。

为每个用户和 MCP Server分别保存provider及其数据，不要跨会话共享 provider。每次待完成的登录都绑定到已认证的应用会话；用户 ID 和会话 ID 从会话中间件读取，不能从回调查询参数获取。

`createMcpSession()` 的流程：

1. 调用 `listTools()`。需要登录时，将浏览器跳转到返回的 `authorizationUrl`。
2. 在回调路由中，对同一会话调用 `completeLogin()`，验证调用者并消费待处理状态，再交换授权码。
3. 使用保存的令牌重新发现工具，返回工具供 Agent 使用。

```ts
const crm = createMcpSession(
  "https://crm.example.com/mcp",
  userId,
  sessionId,
  authProvider,
);

const result = await crm.listTools();

// 存在 result.authorizationUrl：跳转到授权地址。
// 否则：将 result.tools 传给 Agent。
```

在回调完成前，将 `crm` 保留在对应的应用会话中。

#### 完成重定向

用户登录后，授权服务器会跳转到provider的 `redirectUrl`。在该回调路由中，取出同一个 `crm` 实例，以及已验证的用户 ID 和会话 ID，完成登录：

```ts
// 用授权码换取令牌，再使用已保存的令牌重新发现工具。
// 将 result.tools 传给 Agent；如果仍需登录，则再次跳转到授权页面。
const result = await crm.completeLogin(
  new URL(req.url, "http://localhost"),
  userId,
  sessionId,
);
```

辅助函数将完整查询参数传给 `finishAuth()`，供 SDK 验证授权服务器的 `iss` 参数。在交换授权码前，会拒绝缺失、不匹配或已使用的 `state`。

使用工具期间保持适配器开启，应用会话结束时调用 `await crm.close()`。

对于配置了 `transport: "sse"` 的服务器，回调辅助函数应使用 `SSEClientTransport`。无需用户参与的机器间访问，应使用 SDK 的 `ClientCredentialsProvider`，无需浏览器登录。

### 处理身份验证错误

- -
