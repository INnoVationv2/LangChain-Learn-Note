# 上下文工程

上下文工程：**以合适的格式提供必要的信息和Tool，让 Deep Agent 可靠地完成任务。**

Deep Agent 的上下文来源包括：

- **启动时提供**：预先配置的信息。
- **运行时获取**：用户输入等动态信息。

Deep Agent 内置上下文管理机制，支持长时间运行的会话。本页介绍它能访问和管理的各类上下文。

## 1.上下文类型

| 上下文类型       | 可控制的内容                                     | 作用范围                     |
| ---------------- | ------------------------------------------------ | ---------------------------- |
| **输入上下文**   | 启动时提供的System Prompt、Memory、Skill               | 静态内容，每次运行时应用     |
| **运行时上下文** | 调用时传入的固定配置，如用户信息、API 密钥、连接 | 当前运行，并传递给子Agent     |
| **上下文压缩**   | 内置的内容转存和摘要机制，避免超出上下文窗口     | 接近限制时自动执行           |
| **上下文隔离**   | 将繁重任务交给子Agent，只向主Agent返回结果         | 委派任务时，作用于对应子Agent |
| **长期Memory**     | 通过虚拟文件系统跨会话保存信息                   | 跨会话持久保留               |

## 2.输入Context

输入上下文是Agent启动时接收的信息，用于构建Prompt，主要包括以下来源。

1. System Prompt
2. Memory
3. Skill
4. ToolPrompt

### 1.System Prompt

自定义`systemPrompt`会添加到内置System Prompt之前，用来定义Agent的角色、行为和知识。内置Prompt包含文件系统Tool、子Agent等使用说明。

```typescript
const agent = await createDeepAgent({
  model: "openai:gpt-5.5",
  systemPrompt: `You are a research assistant specializing in scientific literature.
  Always cite sources. Use subagents for parallel research on different topics.`,
});
```

- `systemPrompt` 是静态的，不会随着调用改变。

- 如果Prompt需要根据权限、用户偏好等动态生成

  可使用 `dynamicSystemPromptMiddleware`，读取 `request.runtime.context` 和 `request.runtime.store`。

  如果只是Tool需要访问上下文，不用加此中间件, Tool可以直接访问`runtime.context`和`runtime.store`

> 可通过harness profile为特定模型调整Prompt：
>
> | 配置                   | 作用                     |
> | ---------------------- | ------------------------ |
> | `base_system_prompt`   | 完全替换基础Prompt       |
> | `system_prompt_suffix` | 在基础Prompt末尾追加内容 |

### 2.Memory

`AGENTS.md`等Memory文件会**全部加载到System Prompt中**，适合保存项目约定、用户偏好和每次对话都必须遵守的规则。

Memory是全部加载，应保持简短。对于详细流程和领域知识, 应放入Skill。

### 3.Skill

Skill按需加载，减少 token 消耗：

1. 启动时读取各个`SKILL.md`的`frontmatter`。
2. 判断某个Skill相关时，再加载完整内容。

每个Skill聚焦一个流程或领域；正文保持简短，详细参考资料放到单独文件并引用。始终相关的约定放入Memory。

### 4.Tool Prompt

Tool Prompt 指导模型**何时使用工具、如何调用**。工具会向模型提供 schema 和描述。

**内置工具**由 Deep Agents stack 提供，中间件会自动向System Prompt添加使用说明：

- 文件系统：`ls`、`read_file`、`write_file`、`edit_file`、`glob`、`grep`；沙箱后端还支持 `execute`。
- 子Agent：通过 `task` 委派任务。
- 人工介入：设置 `interrupt_on`，在指定工具调用处暂停。
- 本地上下文：当前目录和项目信息，仅限 Deep Agents Code。

**自定义工具**通过 `tools` 参数或中间件添加，应写清名称、用途、使用时机和参数含义。自定义中间件还可以追加System Prompt。

```ts
const searchOrders = tool(
  async ({ userId, status, limit }) =>
    `orders for ${userId} with status ${status} (limit ${limit})`,
  {
    name: "search_orders",
    description: `Search for user orders by status.

Use this when the user asks about order history or wants to check
order status. Always filter by the provided status.`,
    schema: z.object({
      userId: z.string().describe("Unique identifier for the user"),
      status: z
        .enum(["pending", "shipped", "delivered"])
        .describe("Order status to filter by"),
      limit: z
        .number()
        .default(10)
        .describe("Maximum number of results to return"),
    }),
  },
);
```

> **覆盖工具描述**：在 harness profile 中使用 `tool_description_overrides`，以工具名为键，为特定模型替换工具的描述。
>
> **移除无用工具**：内置工具即使未被调用，也会在每轮发送完整 schema。使用 `excluded_tools` 排除不需要的工具，可减少Prompt大小。
>
> 注: 排除工具属于配置优化，不是上下文压缩中的自动转存或摘要。

### 5. 完整System Prompt

Deep Agent 在运行开始时发送给模型的系统消息，由以下部分组成：

1. **自定义Prompt**：`system_prompt`，如果提供。
2. **Agent基础Prompt**。
3. **MemoryPrompt**：`AGENTS.md` 内容及Memory使用指南，仅在提供Memory时加入。
4. **SkillPrompt**：Skill位置、包含 frontmatter 元数据的Skill列表及使用说明，仅在提供Skill时加入。
5. **虚拟文件System Prompt**：文件系统工具说明，以及适用时的 `execute` 工具说明。
6. **子AgentPrompt**：`task` 工具的使用说明。
7. **自定义中间件Prompt**：仅在提供自定义中间件时加入。
8. **人工介入Prompt**：设置 `interrupt_on` 时加入。

## 3.Runtime Context

Agent的**单次运行配置**，用于传递用户信息、API 密钥、数据库连接、功能开关等。

- 不会自动进入Prompt，需由工具或中间件等显式加入消息或System Prompt
- 可用于传递用户元数据（ID、偏好）、API 密钥、数据库连接
- 使用Zod通过 `contextSchema`定义数据结构
- 调用 `invoke` / `ainvoke` 时，通过选项中的 `context` 字段传入
- 通过`runtime.context` 访问
- 会传递给所有SubAgent: 

## 4.上下文压缩

`create_deep_agent`内置上下文压缩，无需额外启用。

长时间运行的任务会产生大量工具输出和对话历史。上下文压缩能减少Memory中的信息量，同时保留任务细节，确保传给LLM的内容不超过上下文窗口限制。

- offload: 大型工具输入和结果会存入文件系统，并在上下文中替换为引用。

- 总结: 当旧消息数量接近限制时，会被压缩成LLM生成的摘要。

在压缩发生前，还可以通过运行框架配置中的 `excluded_tools` 排除未使用的内置工具，减少每轮发送的工具 schema。

### offload

Deep Agents 使用内置文件系统工具自动卸载内容，并按需搜索、读取已卸载的内容。

当工具调用的输入或结果超过 token 阈值（默认 **20,000**）时，会触发以下机制：

1. **工具调用输入超过 20,000 tokens**：文件写入和编辑操作会在对话历史中留下包含完整文件内容的工具调用。由于这些内容已保存到文件系统，通常属于重复信息。当会话上下文超过模型可用窗口的 **85%** 时，Deep Agents 会截断较早的工具调用，将其替换为磁盘文件引用，从而减少当前上下文大小。
2. **工具调用结果超过 20,000 tokens**：Deep Agents 会将结果存入配置的后端，并用文件路径和**前 10 行预览**替换原始结果。Agent随后可以按需重新读取或搜索内容。

> 内置上下文压缩不会调整图片尺寸、降低图片分辨率

### 总结

默认包含SummarizationMiddleware, 当上下文达到触发阈值(例如 `max_input_tokens` 的 **85%**)，且没有更多可卸载的内容时，Deep Agents会自动总结消息历史。

这个过程包含两部分：

- **上下文摘要**：LLM 生成结构化的对话摘要，包括会话目标、已完成的中间成果和下一步操作，用它替换完整对话历史。
- **文件系统保存**：将原始对话消息以文本形式写入文件系统，作为完整的原始记录。

这样，Agent既能通过摘要了解目标和进度，也能在需要时通过文件系统搜索找回文本细节。

**配置：**

- 达到模型配置中`max_input_tokens`的 **85%** 时触发。
- 保留 **10% 的 token 额度**作为近期上下文。
- 如果模型配置不可用，则采用 **170,000 tokens** 的触发阈值，并保留最近 **6 条消息**。
- 如果任何模型调用抛出标准的`ContextOverflowError`，立即生成摘要，并使用“摘要 + 保留的近期消息”重试。
- 模型会对较早的消息进行总结。

## 5.使用SubAgent隔离上下文

SubAgent可以解决**上下文膨胀问题**。使用输出量较大的工具时，上下文窗口会迅速被填满。

SubAgent将这些工作隔离执行，主Agent只接收最终结果，无需接收产生结果的几十次工具调用。还可以为每个SubAgent单独配置模型、工具、System Prompt和Skill。

**工作方式：**

- 主Agent通过 `task` 工具委派任务。
- SubAgent使用独立的全新上下文运行。
- SubAgent自主执行，直到任务完成。
- SubAgent向主Agent返回一份最终报告。
- 主Agent的上下文保持精简。

**最佳实践：**

1. **委派复杂任务**：将会产生大量上下文的多步骤工作交给SubAgent。
2. **保持回复简洁**：要求SubAgent返回摘要，而不是原始数据。
3. **使用文件系统保存大量数据**：SubAgent可以将结果写入文件，主Agent按需读取。

## 6.长期Memory

```ts
const agent = await createDeepAgent({
  model: "openai:gpt-5.5",
  store: new InMemoryStore(),
  backend: new CompositeBackend(new StateBackend(), {
    "/memories/": new StoreBackend({
      namespace: () => ["memories"],
    }),
  }),
  systemPrompt: 'When users tell you their preferences, save them to /memories/user_preferences.txt so you remember them in future conversations.',
});
```

默认文件系统将工作Memory文件保存在**Agent状态**中，仅在单个线程内持久化。长期Memory则可以跨线程、跨对话保存用户偏好、积累的知识和研究进度等信息。

使用长期Memory，需要通过 `CompositeBackend` 将指定路径（通常为 `/memories/`）路由到 **LangGraph Store**。这样，部分文件可以长期保存，其他文件仍只属于单个线程。

无需提前创建Memory文件，只需提供后端配置、Store，并在System Prompt中说明**保存什么、保存在哪里**，例如将用户偏好保存到 `/memories/preferences.txt`。Agent会在获得值得记住的信息时，使用 `write_file`、`edit_file` 按需创建和更新文件。

如果需要预先写入Memory，部署到 LangSmith 时可使用 `Store API`。

## 最佳实践

1. **提供合适的初始上下文**：Memory只保留始终适用的少量约定，任务特定的能力通过专门的Skill提供。
2. **将繁重任务交给SubAgent**：委派多步骤、输出量大的工作，保持主Agent上下文精简。
3. **约束SubAgent输出**：输出过长时，在其 `system_prompt` 中要求返回摘要和归纳后的结论。
4. **用文件保存大型输出**：由SubAgent写入或自动卸载，需要细节时通过 `read_file`、`grep` 获取相关片段。
5. **说明长期Memory结构**：告诉Agent `/memories/` 中保存了什么，以及如何使用。
6. **通过运行时上下文传递配置**：使用 `context` 向工具传递用户元数据、API 密钥等静态配置。
