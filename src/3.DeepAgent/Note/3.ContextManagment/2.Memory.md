## 1.Memory工作原理

1. **指定Memory文件**
   - 创建 Agent 时，通过 `memory` 传入Memory文件路径。
   - 通过 `skills` 传入可复用的任务操作指南，作为**程序性Memory**，告诉 Agent 如何执行任务。
   - `backend` 决定文件存储位置和访问权限。
2. **读取Memory**
   - Memory文件可以在启动时加载到系统提示词，也可以在对话中按需读取。
   - 例如 Skills：启动时只加载技能描述，任务需要时才读取完整文件，减少上下文占用。
3. **更新Memory（可选）**
   - Agent 学到新信息后，可通过`edit_file`工具更新Memory。
   - 默认在对话中更新，也可以通过**后台整合**，在对话之间更新。
   - 修改会持久保存，供后续对话使用。
   - 并非所有Memory都可修改：开发者定义的 Skills 和组织策略通常只读。

常见的Memory作用域：Agent级Memory(所有用户共享) 和 用户级Memory(按用户隔离)

##  3.高级用法

除了Memory path和scope，还可以配置以下维度：

| 维度                  | 回答的问题       | 可选项                                                       |
| --------------------- | ---------------- | ------------------------------------------------------------ |
| **Duration**          | Memory保留多久？ | 短期：单次对话；长期：跨对话                                 |
| **Information type**  | 保存什么信息？   | 情景Memory：过去的经历；程序性Memory：指令和技能；语义Memory：事实 |
| **Scope**             | 谁能查看和修改？ | 用户、Agent或组织                                            |
| **Update strategy**   | 何时写入Memory？ | 对话过程中（默认）或对话之间                                 |
| **Retrieval**         | 如何读取Memory？ | 加载到提示词中（默认）或按需读取，例如技能                   |
| **Agent permissions** | Agent能否写入？  | 读写（默认）或只读，例如共享规则                             |

### 1.情景Memory(Episodic memory)

记录过去的经历：发生了什么、先后顺序以及最终结果。

**情景Memory**存储过去经验的记录：发生了什么、按什么顺序发生以及结果如何, 保留了完整的对话上下文. Agent能回忆起从中学习到的内容，以及问题是如何解决的。

**语义Memory(semantic memory)**保存事实和偏好，存储在`AGENTS.md`等文件中；

Deep Agents通过检查点(checkpointer)支持情景Memory：每次对话都作为带有检查点的线程(thread)持久化保存。

要让Agent搜索历史对话，可以将线程搜索封装成工具。`user_id` 从运行时上下文中提取，而不是通过参数传入。

### 3.背景整合

默认情况下，Agent会在对话过程中写入Memory，称为**热路径（hot path）**。

另一种方式是在**对话之间通过后台任务整理Memory**，也称为**休眠期计算（sleep time compute）**：由独立的 Deep Agent 回顾近期对话，提取关键事实，并与已有Memory合并。

| 方式       | 优点                               | 缺点                                                      |
| ---------- | ---------------------------------- | --------------------------------------------------------- |
| 对话中写入 | Memory立即可用，用户能看到更新过程 | 增加响应延迟，Agent需要同时处理对话和Memory               |
| 后台整理   | 不增加用户等待时间，可综合多次对话 | 新Memory需等整理完成后才能在后续对话使用，需要额外的Agent |

多数应用使用热路径就足够了。当需要降低响应延迟，或提高多次对话形成的Memory质量时，再加入后台整理。

推荐在主Agent旁部署一个**Memory整理Agent（consolidation agent）**，通过 cron 定时触发。执行频率应匹配用户的使用频率：

- 每天持续有对话：每隔几小时整理一次。
- 每周只使用几次：每晚或每周整理一次。

整理过于频繁，会在没有新内容时白白消耗 token。

### 4.只读Memory和可写Memory

默认情况下，Agent可以读取和修改Memory文件。对于组织政策、合规规则等共享内容，可以将Memory设为**只读**，让Agent只能参考，不能修改。

这样可以防止Agent通过修改共享Memory注入恶意指令，确保只有你的应用代码控制文件内容。

| 权限         | 适用场景                                         | 实现方式                                                     |
| ------------ | ------------------------------------------------ | ------------------------------------------------------------ |
| 读写（默认） | 用户偏好、Agent自我改进、学习到的技能            | Agent通过`edit_file`工具修改文件                             |
| 只读         | 组织政策、合规规则、共享知识库、开发者定义的技能 | 由应用代码或Store API写入；通过 `permissions` 禁止Agent修改指定路径, ，或使用Policy hooks实现自定义验证逻辑。 |

**安全注意事项:**如果一个用户能修改另一个用户会读取的Memory，恶意用户就可能向共享内容中注入恶意指令。建议：

- **默认按用户隔离**：使用 `user_id` 划分Memory，有需要时才共享。
- **共享规则设为只读**：由应用代码维护，不允许Agent修改。
- **共享Memory写入前人工审批**：通过 `interrupt` 暂停执行，要求人工批准对敏感路径的写入。

使用 `permissions` 声明哪些路径禁止写入；需要限流、审计日志或内容检查等自定义逻辑时，使用**后端策略钩子（backend policy hooks）**。

### 5.并发写入

多个线程可以并行写入内存，但并发写*同一文件可能会导致“后写优先”冲突。

对于用户级内存，这种情况很少见，因为用户通常一次只进行一个对话。

对于代理级或组织级内存，可以使用**后台合并**来串行写入，或者将内存结构化为每个Topic的单独文件，以减少争用。实际上，如果写入操作因冲突而失败，LLM 通常足够智能，可以重试或优雅地恢复，因此丢失一次写入操作不会造成灾难性后果。

### 6.同一部署中的多个Agent

要在共享部署中为每个代理分配独立的内存，可使用`assistant_id`添加到命名空间：

```ts
new StoreBackend({
  namespace: (rt) => [
    rt.serverInfo.assistantId,
    rt.serverInfo.user.identity,
  ],
})
```
