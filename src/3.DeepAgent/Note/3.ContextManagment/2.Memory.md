## 1.Memory工作原理

1. **指定Memory文件**
   -`memory`：指定Memory文件路径.
   -`skills`：提供可复用的任务操作步骤, 属于**程序性Memory**.
   - Backend：决定文件存在哪里、如何划分访问范围.
2. **读取Memory**
   - Memory文件可以在启动时加载到System Prompt, 也可以在对话中按需读取.
   - Skill 启动时只加载简介, 遇到相关任务才读取完整文件, 减少上下文占用.
3. **更新Memory(可选)**
   - Agent 学到新信息后, 可以通过`edit_file`修改Memory.
   - 可以在对话中更新, 也可以在对话之间由后台任务整理.
   - 持久化后, 后续对话可以继续使用.
   - 开发者定义的 Skill、组织政策通常设为只读.

常见的Memory范围：

| 范围         | 共享方式                    |
| ------------ | --------------------------- |
| Agent 级Memory | 同一个 Agent 的所有用户共享 |
| 用户级Memory   | 每个用户独立保存            |

## 3.高级用法

### 1.情景记忆(Episodic memory)

**Agent 不仅能记住结论, 还能回顾过去解决问题的完整过程.**

- **语义Memory**：记录事实、偏好或经验, 例如“这个项目使用 TypeScript”.
- **情景Memory**：记录一次任务的经历, 例如“遇到什么报错 → 排查了哪些地方 → 如何修复 → 结果怎样”.

Deep Agents 用 **checkpointer** 保存对话和执行状态, 为情景Memory提供基础.要让 Agent **搜索以前的对话**, 还需要把对话搜索封装成Tool.

搜索时,`user_id`从运行时上下文读取, 不让模型作为Tool参数传入, 用来限定当前用户的记录.

```ts
// Search conversations for a specific user
const userThreads = await client.threads.search({
  metadata: { userId },
  limit: 5,
});

// Search conversations across an organization
const orgThreads = await client.threads.search({
  metadata: { orgId },
  limit: 5,
});
```

### 2. 组织级Memory

同时配置用户个人Memory和组织共享Memory, 并把它们存到不同的空间.

```ts
import { createDeepAgent, CompositeBackend, StateBackend, StoreBackend } from "deepagents";

const agent = createDeepAgent({
  memory: [
    "/memories/preferences.md",
    "/policies/compliance.md",
  ],
  backend: new CompositeBackend(
    new StateBackend(),
    {
      "/memories/": new StoreBackend({
        namespace: (rt) => [rt.serverInfo.user.identity],
      }),
      "/policies/": new StoreBackend({
        namespace: (rt) => [rt.context.orgId],
      }),
    },
  ),
});
```

通过应用程序写入组织Memory：

```ts
const client = new Client({ apiUrl: "<DEPLOYMENT_URL>" });
await client.store.putItem(
  [orgId],
  "/compliance.md",
  createFileData(`## Compliance policies
- Never disclose internal pricing
- Always include disclaimers on financial advice
`),
);
```

### 3.Memory整理

**可以把Memory整理放到对话结束后, 由另一个 Agent 在后台完成.**

两种方式：

| 方式                   | 如何处理                                          | 优点                           | 缺点                                     |
| ---------------------- | ------------------------------------------------- | ------------------------------ | ---------------------------------------- |
| 对话中写入(Hot path) | 主 Agent 一边聊天, 一边更新Memory                   | Memory立即可用                   | 增加回复耗时, 需要兼顾聊天和Memory         |
| 后台整理(Background) | 单独的 Agent 回顾近期对话、提取事实、合并已有Memory | 不影响回复速度, 能综合多次对话 | 更新后的Memory稍后才可用, 需要第二个 Agent |

例如, 用户在几次对话中提到“正在学 TypeScript”“喜欢简短回答”, 后台 Agent 可以统一整理成用户偏好, 供后续对话使用.这也叫 **sleep time compute**, 即利用对话间隙进行计算.

推荐做法是：在`langgraph.json`中同时注册主 Agent 和**Memory整理 Agent(consolidation agent)**, 用cron定时触发整理.

频率按使用量决定：每天频繁聊天可以每隔几小时整理；每周只用几次, 可以每晚或每周整理.运行过于频繁, 只会浪费 token.

**多数应用在对话中写入Memory就够了**；需要降低回复延迟或综合大量对话时, 再增加后台整理.

### 4.只读Memory和可写Memory

Memory 默认可读写.组织政策、合规规则等共享内容应设为**只读**, 由应用代码维护, 防止Agent修改并注入恶意指令.

| permissions         | 适用场景                                         | 实现方式                                                     |
| ------------ | ------------------------------------------------ | ------------------------------------------------------------ |
| 读写(默认) | 用户偏好、Agent自我改进、学到的Skill            | Agent通过`edit_file`修改                             |
| 只读         | 组织政策、共享知识库、开发者定义的 Skill | 由应用代码或Store API写入；通过`permissions`禁止Agent修改, 或使用Policy hooks实现自定义逻辑. |

**安全建议:**如果一个用户能修改另一个用户的Memory, 恶意用户就可能向共享内容中注入恶意指令：

- **按用户隔离**：用`user_id`划分 Memory, 按需共享.
- **共享规则设为只读**：由应用代码维护, 不允许Agent修改.
- **敏感写入需审批**：通过`interrupt`暂停执行, 等待人工批准敏感路径的写入.

用`permissions`限制写入路径；用 Backend Policy Hooks 实现限流、审计或内容检查.

### 5.并发写入

多个线程可以并行写入内存, 但并发写*同一文件可能会导致“后写优先”冲突.

对于用户级内存, 这种情况很少见, 因为用户通常一次只进行一个对话.

对于Agent级或组织级内存, 可以使用**后台合并**来串行写入, 或者将内存结构化为每个Topic的单独文件, 以减少争用.实际上, 如果写入操作因冲突而失败, LLM 通常足够智能, 可以重试或优雅地恢复, 因此丢失一次写入操作不会造成灾难性后果.

### 6.同一部署中的多个Agent

要在共享部署中为每个Agent分配独立的内存, 可使用`assistant_id`添加到namespace：

```ts
new StoreBackend({
  namespace: (rt) => [
    rt.serverInfo.assistantId,
    rt.serverInfo.user.identity,
  ],
})
```
