# 人工审批

## 1.基本配置

- `interrupt_on` 用来设置哪些工具需要暂停执行、等待人工审核，以及审核时允许哪些操作。有以下参数:
  - **`True`**：开启人工审核，允许批准、编辑或拒绝。
  - **`False`**：关闭人工审核。
  - **`InterruptOnConfig`**：自定义审核规则，通过 `allowed_decisions` 指定允许的审核操作。

## 2.Decision 类型

`allowed_decisions`控制人工审核时，可以选择哪些操作：

| 操作      | 说明                                         |
| --------- | -------------------------------------------- |
| `approve` | 按智能体提供的参数继续执行                   |
| `edit`    | 修改参数后再执行                             |
| `reject`  | 不执行此次工具调用，并将拒绝原因反馈给智能体 |

> **修改工具参数时，尽量只做必要的小幅调整: ** 大幅修改可能会让模型重新考虑执行方案，导致重复调用工具或采取意料之外的操作。

可以为每个工具单独设置Decision。

```ts
const interruptOn = {
  // Sensitive operations: allow all options
  delete_file: { allowedDecisions: ["approve", "edit", "reject"] },

  // Moderate risk: approval or rejection only
  write_file: { allowedDecisions: ["approve", "reject"] },

  // Must approve (no rejection allowed)
  critical_operation: { allowedDecisions: ["approve"] },
};
```

## 3.处理中断

触发中断时，智能体会暂停执行并交回控制权。此时需要检查返回的中断信息，进行相应处理。

如果用户拒绝执行某个操作，应明确告知智能体：工具未执行以及接下来该做什么。

## 4.在Streaming中处理中断

对于实时用户界面，用`.stream()`代替`.invoke()`，可以一边显示模型生成的文字和工具调用进度，一边处理人工审核中断(HITL)。

中断信息会以`__interrupt__`的形式出现在 `updates` 流中。流结束后，收集人工审核决定，再通过`Command(resume=...)`重新启动流式执行。

> 对于常见的`interrupt_on`，恢复时传入以下结构，与`.invoke()`用法相同：
>
> ```ts
> {"decisions": [...]}
> ```
>
> 如果有多个中断等待处理，则将每个中断ID映射到其恢复值.

通常, 一个中断里, 包含多个待审批的工具调用。例如：

```ts
const interrupts = [{
    id: "interrupt-1",
    value: {
        actionRequests: [
            { name: "get_weather", args: { city: "NY" } },
            { name: "send_email", args: { to: "a@example.com" } },
        ],
    },
}];
```

虽然有两个工具调用，但只有**一个中断**。按**工具调用顺序**提供两个决定即可：

如果存在**多个独立中断**，例如并行分支分别暂停，就需要用 ID 指明每份决定属于哪个中断：

```ts
streamInput = new Command({
    resume: {
        "interrupt-1": {
            decisions: [{ type: "approve" }],
        },
        "interrupt-2": {
            decisions: [{ type: "reject", message: "取消操作" }],
        },
    },
});
```

同时使用 `"messages"` 和 `"updates"` 两种流模式，可以兼顾实时文字展示和中断处理：

- `messages`：实时输出模型生成的文字。
- `updates`：传递中断信息。

## 多个工具调用

如果智能体一次调用多个需要审核的工具，这些调用会合并到同一次中断中。你必须按顺序为每个工具调用提供审核决定。

## 拒绝反馈

审核人选择 `reject` 后，Deep Agents 会跳过该工具调用，并将拒绝反馈发送给智能体。

如果没有提供 `message`，默认反馈会告诉模型：工具没有执行，除非用户要求，否则不要重试同一次工具调用。

对于涉及敏感操作或会产生实际影响的工具，应通过 `message` 提供符合具体业务场景的说明，明确告诉智能体接下来应该：

- 放弃该操作；
- 向用户进一步确认；
- 尝试更安全的替代方案。

## 修改工具参数

如果允许的审核操作中包含 `"edit"`，审核人就可以在工具执行前修改参数。

## 子智能体中断

使用子智能体时，可以在**调用工具前**触发中断，也可以在**工具执行过程中**触发中断。

### 调用工具前中断

每个子智能体都可以单独设置 `interrupt_on`，覆盖主智能体的配置。

子智能体触发中断后，处理方式相同：检查返回结果中的 `__interrupt__`，再通过 `Command` 恢复执行。

在流式输出中，子智能体的中断也会以 `__interrupt__` 条目的形式出现在父智能体的 `updates` 流中，无需设置 `subgraphs=True`。

如果还想实时获取子智能体生成的文字和执行进度，则需要开启 `subgraphs=True`。

### 工具执行过程中中断

子智能体的工具可以直接调用 `interrupt()`，暂停执行并等待人工批准。
